# Audit disposition for 0.3.1

This page records what happened to each finding of the external code audit of 0.3.0 (Gemini's expanded audit, independently spot-checked by ChatGPT against `main` at `e89dc98`). Each finding was checked against the source before anything was changed. Source-level findings are kept apart from failures that were actually reproduced.

**Baseline:** `main` at `e89dc98`, 96 of 96 unit tests passing on Linux (GCC 13, Ubuntu 24.04).
**Candidate:** the `v0.3.1` tag. 113 unit tests pass on Linux, also under AddressSanitizer with UndefinedBehaviorSanitizer (no findings) and ThreadSanitizer (reports only inside Pango, fontconfig and GLib, none in Tonearm code). The Windows CI job builds with MSVC, runs the same suite with DirectWrite and packages the zip.

**What has not been done:** Tonearm 0.3.1 has not been loaded in OBS on Windows. The planned 12-hour soak test on the author's PC did not start, so there are no soak, GPU or gaming benchmark results, and no measured before/after performance numbers. Everything below about runtime behaviour on Windows is reasoned from the source and from the documented WinHTTP, Direct2D and libobs contracts, not observed.

| 3 | Outage falls through to the catalog fallback | Confirmed | The catalog fallback is skipped when the lookup service itself failed. |

## Deferred: cancelling requests in flight

Network requests stay synchronous WinHTTP calls with per-call timeouts (2.5 to 7 seconds). Closing the request handle from another thread while a synchronous call is running is not a documented way to cancel it, and moving to asynchronous WinHTTP (callbacks, handle-closing notifications, an explicit owner for each handle) is a larger change than a patch release should carry without runtime testing on Windows. The effect is unchanged from 0.3.0: switching animated artwork off, changing its settings or removing a source while a lookup is stuck can block that action until the current request times out. The outage backoff added in 0.3.1 makes that less likely, because no requests are sent while the service is known to be down.

## Points for an independent review

- `src/obs/motion-player.cpp`: the configure generation, the lease of the loaded video, the paused-capture skip and `releaseGraphics()`.
- `src/obs/http-client.cpp`: redirect handling, header parsing, size cap and the `sink` path; `src/media/net_policy.cpp` for the URL grammar.
- `src/media/cache_budget.cpp`: what may be deleted, the lease checks, rename-before-delete, and the Windows behaviour of `symlink_status` on junctions.
- `src/obs/settings.cpp`: `migrateSettings` (called once from the source constructor) and import validation.
- `src/text/text_dwrite.cpp`: COM ownership and `addFontFiles`.

## Before calling it production-ready

Per the handoff's own rule, 0.3.1 should be treated as **conditional**: the unit tests and sanitizers pass and the Windows build is produced by CI, but these remain:

1. Load the 0.3.1 zip in a portable OBS on Windows and run the [Windows test plan](../testing.md#windows-test-plan), including animated artwork on SOS, Wonder, Merry Christmas, Positions and 143.
2. Run the 12-hour soak test once it can start on the author's PC.
3. Compare OBS's Stats (render time, skipped frames) and GPU video decode with 0.3.0 under the same scene, for the benchmark the handoff describes.
